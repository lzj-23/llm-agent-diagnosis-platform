# 数据与状态设计

## 表结构

- tasks：UUID 主键、会话 ID、幂等键（唯一）、请求指纹、问题、案例 ID、执行模式、状态、结果 JSON、创建和更新时间、执行租约。
- events：任务 ID 外键、递增序号、角色、动作、输入输出 JSON、耗时、错误；任务与序号联合唯一。
- memories：会话 ID、任务 ID、已完成诊断摘要；仅保存已审核结果，查询时明确作为历史参考。

PostgreSQL 是事实来源，Redis 仅作短期缓存与任务通知。缓存不可用时直接读数据库；通知丢失由数据库扫描恢复。领取任务使用数据库锁与租约，避免多进程重复领取；到期任务可恢复。模型调用无法提供跨故障的 exactly-once 保证，重试可能计费，预算预留必须在调用前完成。

## 状态流转

pending -> running -> completed / needs_attention。
needs_attention 只有显式恢复才回到 pending，避免欠费或权限错误下持续消耗。
进程崩溃后的 running 任务通过租约过期回收；已有证据和事件留存。

## 任务过程

Planner 输出证据收集计划；Executor 通过真实 MCP stdio 会话选择并调用六个白名单工具；Reviewer 使用当前证据审核草稿。系统再次校验引用 ID 与必需工具覆盖。报告只说明候选原因和验证步骤。

## 记忆边界

- 工作记忆：当前任务已收集的证据与状态检查点。
- 短期记忆：同一 session 的最近已完成任务摘要。
- 长期记忆：按问题检索历史已审核诊断，不能覆盖当前测量事实。

## 本地与部署

本地轻量开发可使用 SQLite，但其测试不能证明 PostgreSQL 锁语义和多进程行为。正式验收必须包含 PostgreSQL、Redis 和容器环境。开发端口只绑定本机；公开部署需要认证、HTTPS 和请求额度控制。
