# 有限修订与失败分析

## 为什么继续做

首次发布的single-config-0报告把“没有OOM日志、指标不变”写成可以排除资源风险。旧系统只拦截并转人工，没有反馈修订环节。

现在在报告生成前增加一次quality_repair模型调用：输入原报告、具体审计问题和已经收集的证据，禁止新增测量或调用修复工具。候选报告需要重新通过结构、非空引用、引用ID范围和原有质量检查。失败、超时、预算不足或引用伪造都保留原报告和审计问题，仍为needs_attention。取消请求不被吞掉。原稿、候选、是否接受和调用用量均进入事件记录。

这不是无限重试，不保证语义正确；quality_repair=False可关闭新增步骤。后续消融必须明确这一开关，旧的单Agent/无Reviewer结果不可直接与默认开启修订的新版本比较。

## 发现的具体问题

1. quality-repair-v1：原案例看似通过，但逐条阅读发现“不充分排除结论”被后面一句否定措辞掩盖。改为按分句检查，增加回归测试。
2. 同一批中，“无法确认故障状态或声称已修复”被误认作修复成功。增加否定语境测试。
3. 分句改动一度误拦未来的验证步骤。失败JUnit保存在quality-repair-v2；调整计划动作的判断后恢复测试。
4. quality-repair-final仍有一个保守误报：建议“检查服务配置中是否误将并发上限设置为QPS目标值”被check_units标记。保留原稿和候选供人工复核，没有删掉该失败。

## 证据范围

- quality-repair-final/integration-tests.xml：54项自动化测试，包括一次修订、关闭修订、超时、预算失败、无引用、伪造引用、无效JSON与取消传播。
- quality-repair-final：1个历史失败和4个手写挑战，真实模型调用，4/5通过规则检查；它们是开发回归，不是独立盲测，不代表生产正确率。逐条查看revised与events才能区分误报和真实错误。
- repair-e2e-v1运行期间源代码有改动，不作冻结验收。
- repair-e2e-final是后续冻结代码的完整流程复测：4/4任务达到completed、4个类别命中，source_unchanged=true，估算调用费0.0463903元。OOM任务触发一次修订，其他三个未触发。该批次不是旧失败修复率或生产准确率。

## 对最终报告的人工式逐条检查

此处为开发者阅读检查，不是独立专家标注。原失败报告在专门修订实验中不再根据无OOM日志排除资源风险；缺失证据报告保留unknown，矛盾证据报告保留待验证假设。

完整流程仍有规则漏检：config结论写“而非计算/排队瓶颈或OOM”，OOM结论写“直接失败并快速返回，而非排队或算力饱和”。现有日志和聚合指标不足以排除其他共存因素或证明失败返回路径。这些表达未触发当前关键词规则。因此4/4 completed不等于4/4语义完全正确；现阶段报告仍需人工核对。继续堆关键词不能替代逐条证据支持关系的评测，后续需建立独立标注集和声明级检查。

## 仍需补充

后续容器验收repair-neural-final出现Reviewer输出截断（1200输出token，JSON不完整）。已保留失败任务；模型客户端新增finish_reason=length检测，对非工具输出最多追加一次短JSON重试，两次调用用量都记录，仍截断则返回model_output_truncated。新增两项测试后总计56项通过（truncation-tests.xml）。repair-e2e-final指纹对应这项客户端修正之前的冻结代码，不冒充最新客户端的完整矩阵验收。

重建神经检索镜像后，repair-neural-retest端到端任务completed，网页资源正常，实际检索后端为neural_sqlite_exact_cosine_crossencoder。单次成功不是稳定成功率；截断重试路径的确定性覆盖以两项模拟响应测试为准。

当前没有独立第三方标注的真实事故集；规则检查不能证明引用内容充分支持每一句话。大规模语义评测、真实GPU OOM、公网实时访问和生产容量验证仍未完成。此轮没有购买服务器，也没有开放公网付费API。
