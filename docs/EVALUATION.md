# 评测设计与诚实解释

## 数据与实验组

`tools/fixtures.py` 生成延迟、OOM、配置错误、正常四个基础模板，每个有三个轻微变体。Synthetic v2 另含96例、8种挑战场景和开发/验证/冻结分组，设计与首轮实跑见 [SYNTHETIC_DATASET.md](SYNTHETIC_DATASET.md)。所有数据均明确 synthetic，不是从生产事故库采样。

single：单 Executor；multi：Planner + Executor + Reviewer；no-rag：多 Agent 禁用检索工具；no-reviewer：多 Agent 无审核。默认评测用词项检索；`neural-mcp` 是单独的 BGE/CrossEncoder 集成验证。

模型 temperature=0、max_tokens=1200，真实供应商 API。temperature=0 仍不保证结果完全一致。每个案例无历史记忆，避免组间记忆污染。运行时延包含模型请求和 MCP 子进程启动；神经模式包括模型加载，不是纯检索延迟。

## 指标定义

- 完成率：completed / 全部任务。
- 故障类别命中率：category 等于模板标签 / 全部任务。不是定位到真实硬件根因。
- 工具白名单率：调用工具在合法列表中的比例。
- 参数 schema 合法率：参数能通过结构校验的比例。参数语义正确性需另审。
- 引用存在率：引用 ID 存在于本次收集证据中的比例。不能命名为语义引用正确率。
- 时延：总时延均值、中位数和线性插值 P95。
- 用量/费用：API usage 和配置价格估算；失败响应可能缺 usage。
- 检索调用数：RAG 开启仅允许调用，模型可不调用；没有真正调用时不能声称该样本获得 RAG 增益。

`summarize_evaluation.py` 重算上述指标。原始 JSON 保留模型、工具、审核事件；CSV 保留每项结果，包括失败，不挑掉失败样本。

## 人工语义评分规范

每份报告逐句核对：(1) 数值是否与指标一致；(2) 引用能否支持相应论断；(3) 是否把相关性写成确定根因；(4) 是否虚构修复效果；(5) 工具是否适合当前问题、case_id 是否正确。使用“支持 / 合理但待验证 / 不支持”三级标注。

幻觉率应以“不支持论断数 / 被核查的事实论断数”计算。没有逐句标注的报告，该字段保持 null，**不是 0%**。模型审核器可以辅助，但不能自证无幻觉。本次开发人员复核也不是独立盲评，应注明审阅者性质。

## 失败分析

早期单 Agent 把 waiting=28 与 32-16 相等联系起来，这是实际错误，原始记录保存在 single-initial。早期审核也会仅复述报告。随后改为 issues + revised 的审核契约，并强调算术、证据缺口与因果边界。

即便四个类别全部命中，也不能证明审核器显著优于单 Agent，因为样本少、模板简单、随机性和供应商延迟未控制。优先展示失败、修订和验证链，而不是包装一个漂亮的准确率。

## 扩展路线

附加的 `judge_evaluation.py` 使用真实模型对最终报告选取最多 6 条结论论断核查，保存原始裁判输出和 quote 连续子串校验结果。`judge-summary.json` 的工具选择、参数语义、引用支持和不支持论断率都是**同模型裁判估计**，不是人工真值。开发复核见 MANUAL_REVIEW.md；两者不一致时不得挑选更好看的指标。

已补充开发者编写的缺失遥测、冲突证据和多故障混合案例，但它们仍不是独立构造或真实事故。下一步需要引入授权脱敏的真实压测事故、第三方或双人盲评、重复多轮与跨模型测试。这些不作为本次已完成生产验证的经历。
