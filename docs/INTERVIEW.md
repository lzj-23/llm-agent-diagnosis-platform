# 演示与面试材料

这些是项目实现的讲解稿，不是虚构实习经历。请先亲自运行、修改并理解关键模块，再按实际参与情况描述自己的贡献。没有生产用户、线上收益或独立完成的证据，就不要这样写。

## 三分钟演示

1. 打开工作台，说明这是离线证据辅助诊断，不会操作生产服务器。
2. 选择 latency-0，多 Agent 模式。先看基线/当前并发条件，说明 synthetic 标签。
3. 提交后展开 Planner 计划、Executor 工具参数/结果、Reviewer issues。
4. 打开最终报告，指出候选原因、证据 ID、不确定性和控制变量复测步骤。
5. 切换 oom-0、config-0 展示不同类别；正常案例说明不能凭空猜测异常。
6. 打开历史任务；刷新网页仍能看到报告。下载 JSON，说明 PostgreSQL 持久化。
7. 查看 final-ablation 评测；说明小样本不证明多 Agent 显著优于单 Agent。
8. 最后展示早期错误算术案例和修订过程，比只展示成功截图更能说明工程判断。

## 一分钟介绍（理解后使用）

我先把问题限定在推理服务延迟、显存不足和参数配置三类，避免一开始做一个什么都回答的聊天机器人。接着把日志、指标、实验对比和文档检索封装成六个只读工具，通过 MCP 提供给 Agent。然后我把流程拆成规划、执行和审核三个角色，用数据库记录每一步证据和任务状态。最后我补了幂等、失败重试、租约恢复、链路追踪以及对照评测。它目前是可以部署和演示的工程原型，公开验证用合成案例，不能代表生产准确率，也不会自动修改服务器。

## 常见追问

### 1. 为什么不是一次大模型问答？

我需要的是先取证再下结论。单次问答不能保证读取了当前日志和测量条件，所以我让工具返回结构化事实，再让模型引用这些事实。这样发现错误时可以定位到取证、解释还是审核环节。

### 2. 多 Agent 到底体现在哪里？

Planner 只产出取证计划，Executor 根据工具结果继续调用并生成草稿，Reviewer 只看问题、草稿和证据独立审核。它们是同一模型的不同角色调用，不是三个模型并行训练。是否值得增加审核成本要用对照实验判断。

### 3. MCP 和 Function Calling 有什么区别？

模型用 Tool Calling 表达想调用哪个工具和参数，应用负责校验。校验后通过 MCP 客户端把请求送给独立工具进程。前者解决模型如何提出工具调用，后者解决应用如何标准化连接工具服务。我的项目实际经过 stdio JSON-RPC，不是只给本地函数起了 MCP 的名字。

### 4. 怎么防止无限循环？

我限制最多六轮、每轮最多六个工具，模型和工具各有有限超时重试，调用前做预算预留。超过边界就进入需要人工处理状态，保留证据，不让它一直扣费。

### 5. 引用了资料就没有幻觉吗？

不是。我遇到过模型引用真实指标，却把 32 减 16 与 28 联系起来。引用 ID 存在只说明找得到资料，不说明计算和解释正确。因此我保留原始草稿，让 Reviewer 检查问题，并把语义正确性单独列为人工评分项。

### 6. 为什么先做单 Agent？

我先确认模型能够正确选择工具、传参、读取结果并生成报告。这个闭环不通时，增加角色只会让排查更复杂。单 Agent 同时也是多 Agent 的成本和质量基线。

### 7. 如何区分排队与算力瓶颈？

我先看 TTFT、E2E、吞吐和排队日志，再核对并发变化。如果吞吐几乎不增长而排队明显增加，可以把饱和列为候选，但没有 GPU 利用率、带宽和 preemption 数据，就不能确定是哪一种硬件或调度瓶颈。需要控制变量复测。

### 8. RAG 用了什么？

我保留一个词项检索基线，再实现 BGE Embedding、SQLite 保存向量、余弦召回和 CrossEncoder 重排。向量库是小语料精确扫描，不是大规模 ANN。当前知识资料很小，重点是完整链路和可追溯引用，不夸大知识覆盖。

### 9. 为什么 PostgreSQL 和 Redis 都要用？

PostgreSQL 保存权威任务、事件和历史摘要，也承担持久化任务队列。Redis 只缓存短时状态快照，出问题可以回数据库。不能因为用了 Redis 就说实现了分布式消息队列。

### 10. 两个 Worker 怎么避免抢到同一个任务？

我用 PostgreSQL 行锁加 SKIP LOCKED，任务取得所有者和租约。写事件和结果时检查所有者，旧 Worker 即使回来也不能覆盖新 Worker。实际做了八路并发抢占和过期接管测试。

### 11. 服务重启后会怎样？

已经写入数据库的证据保留。运行中的任务租约过期后能被接管，重新构建取证上下文。但外部模型响应如果在断电时未保存，可能重复请求，所以我不保证 exactly-once 和零重复计费。

### 12. 重试策略是什么？

429、部分 5xx 和网络超时可以有限重试；认证错误重试没有意义。工具失败最多重试两次，模型瞬态错误最多三次。最终仍失败就让用户查看轨迹并处理，而不是伪造成功报告。

### 13. 如何防止 Prompt 注入？

我把用户描述和日志都当不可信输入，做基础拦截和脱敏，但不把正则当绝对防线。真正的底线是工具白名单和参数范围：系统根本没有 shell 或生产修改工具，模型说要执行也不会被允许。

### 14. 如何统计成本？

成功响应记录供应商返回的输入输出 token，再按配置单价估算。调用前另有保守预留账本，用事务防止并发超预算。失败请求可能没有 usage，预留值也不是最终账单；换模型必须换单价。

### 15. 怎样证明多 Agent 更好？

不能只凭架构证明。我跑相同案例的单、多 Agent、无 RAG、无 Reviewer 四组，记录原始输出、类别命中、时延和费用。目前模板样本少，最多说明链路可以比较，不能得出统计显著的优越结论。

### 16. 做到了生产级吗？

我实现了若干生产工程机制，例如持久化、幂等、有限并发、重试、安全边界和可观测性，但项目仍是单用户工程原型。还缺授权真实事故集、多租户、SSO、HA、备份恢复和生产负载验证。

### 17. 真实遇到最难的问题是什么？

一类是模型结论看着合理但证据不支持，我通过保存草稿和结构化审核把问题暴露出来。另一类是 Windows 下神经检索在 MCP 运行后导入数值库卡住，我用线程栈定位到 NumPy 导入，随后改为进程启动前预加载并限制计算线程，重新验证真实 MCP 链路。

### 18. replay_case 是真的重跑推理吗？

不是。它重新执行注册案例的离线规则检查，没有启动 vLLM、生成 GPU 测量或验证修复效果。我在工具说明和报告中保留这个边界。
