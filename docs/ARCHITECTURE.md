# 系统架构（早期准备稿）

本文件保留早期方案讨论，最终三角色、任务租约、存储与 RAG 实现以 [SYSTEM_DESIGN.md](SYSTEM_DESIGN.md) 为准，不把这里的未实施设想写进简历。

## 1. 总体结构

```text
用户/前端
   |
FastAPI API
   |
任务服务 ---- PostgreSQL（任务、证据、结论）
   |              Redis（队列、短期状态、锁）
编排器
   |-- 指标 Agent ---- 推理结果适配器
   |-- 日志 Agent ---- 日志解析工具
   |-- 知识 Agent ---- RAG/知识库适配器
   |-- 诊断 Agent ---- 候选根因生成
   |-- 审核 Agent ---- 证据与冲突检查
   `-- 报告 Agent ---- 结构化报告
          |
日志、指标、Trace、评测集
```

## 2. 为什么先工具、后 Agent

TTFT 分位数、错误频次、时间窗口聚合、配置差异等事实应由确定性代码计算。Agent 负责选择工具、组合证据和解释，不负责凭空计算。这样更容易测试，也能降低幻觉。

## 3. Agent 状态

一次诊断任务至少保存：任务 ID、用户问题、输入数据引用、当前步骤、工具调用、证据、候选根因、审核意见、最终报告、错误和时间消耗。状态必须可序列化，后续才能恢复、重试和审计。

## 4. 数据边界

### 推理评测适配器

读取既有结果中的 `case`、`protocol`、`summary`、`resources` 和 `requests`，重点标准化 TTFT、E2E、请求吞吐、输出 token 吞吐、成功率和资源数据。任何比较必须保留模型、设备、上下文、并发、请求数等测试条件。

### RAG 适配器

读取检索耗时、生成耗时、总耗时、引用、数据集规模和评测汇总。现有 FastAPI 请求/响应模型只作为兼容参考，新项目通过独立 DTO 解耦。

### 隐私与仓库边界

适配器默认关闭，只有显式配置外部路径后才可读取。API Key 只来自环境变量，日志写入前脱敏，仓库只提交合成数据。

## 5. 可靠性设计

- 每个工具设置超时、重试上限和结构化错误
- Agent 输出使用 Pydantic 校验
- 同一任务使用幂等键，避免重复执行
- 单个 Agent 失败可生成部分报告并标记缺失证据
- 写数据库和调用外部工具分别记录状态
- 审核 Agent 不能修改原始证据，只能添加审核结论

## 6. 可观测性

每次任务记录 request ID、task ID、agent 名称、工具名称、耗时、token 用量、重试次数和错误类型。阶段性指标包括任务成功率、P50/P95 总耗时、工具失败率、证据覆盖率和单任务模型成本。

## 7. 技术选型

- Python 3.10-3.12、FastAPI、Pydantic
- PostgreSQL 持久化，Redis 支持队列和短期状态
- Agent 编排框架在单 Agent MVP 完成后再选；先验证状态模型，避免被框架绑死
- OpenAI 兼容模型接口，便于更换服务
- pytest、ruff、Docker Compose

前期不提前引入 LangGraph、向量数据库和前端框架；它们应在接口和评测场景明确后按需求加入。
