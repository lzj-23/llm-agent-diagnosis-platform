# 产品需求文档

## 1. 项目定位

本项目不是通用聊天机器人，而是一个面向大模型应用服务的工程诊断 Agent。它把分散的服务日志、推理性能指标、RAG 评测结果和运维知识组织成可追溯的诊断流程，输出“发生了什么、证据是什么、可能原因、建议先做什么”。

## 2. 目标用户

- 开发大模型应用的后端工程师
- 负责推理服务和 RAG 系统的测试或平台工程师
- 需要快速定位线上或压测异常的项目成员

## 3. 核心问题

现有信息通常分散在日志、指标文件和文档中，人工排查需要反复切换工具；单次大模型问答又容易缺少证据、跳过验证或提出不可执行建议。本项目用确定性工具先提取事实，再由多个 Agent 分工推理，并保存完整证据链。

## 4. MVP 范围

### 输入

- JSON/JSONL 服务日志或合成日志
- 推理评测结果：TTFT、端到端延迟、吞吐、成功率、CPU/GPU/内存等
- RAG 评测结果：检索耗时、命中情况、引用和回答质量摘要
- 用户的自然语言诊断问题

### 处理

1. 校验并标准化输入；
2. Planner 制定取证计划；
3. Executor 通过 MCP 查询日志、指标、历史对比与资料；
4. Executor 形成候选诊断；
5. Reviewer 列出草稿问题并修订；
6. 系统校验实际引用，组装报告并持久化。

### 输出

- 故障类别和异常摘要
- 引用来源与明确的不确定性，不输出未经校准的置信概率
- 候选根因，不把相关性冒充因果
- 可执行建议、预期影响和验证方式
- 完整 Agent 执行轨迹与失败信息

## 5. 明确不做

- 不自动修改生产配置或执行危险命令
- 不把模型判断写成已确认的根因
- 不在 MVP 中训练或微调基础模型
- 不宣称覆盖所有监控系统和模型服务
- 不复制两个既有项目的代码来凑功能

## 6. 成功标准

- 四类合成场景均可重复运行并产生结构化报告
- 关键结论都有证据引用或明确标注“证据不足”
- 工具失败、模型超时和无结果时能降级，不导致整条任务无响应
- 诊断质量、端到端耗时和模型调用成本可被量化
- 新人按照 README 能在本地完成启动和测试

## 7. 面试价值

项目重点展示 Agent 编排、工具调用、RAG、结构化输出、异步任务、状态持久化、可靠性、可观测性、评测和后端工程能力。所有简历指标必须等最终实测后再填写。
